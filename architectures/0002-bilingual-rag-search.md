# 0002. 이중 언어(한/영) 동시 검색으로 교차언어 임베딩 약점 우회

- 상태: 채택
- 관련 코드: `src/agent/retriever.py`의 `rag_search()`, `_translate()`, `_vector_search()`

## 맥락
대상 문서(HADOOP2 스페이스)는 전부 영어인데, 실제 사용자는 한국어로 질문합니다. 한국어 질의를 그대로 `amazon.titan-embed-text-v2:0`로 임베딩해서 검색해봤더니, 정답 문서의 top1 유사도가 실측 ~0.13까지 떨어졌습니다(영어 질의로 같은 문서를 검색하면 0.4~0.8대). Titan Embed v2의 교차언어(한↔영) 유사도가 동일언어 대비 크게 낮다는 것을 실측으로 확인했습니다.

## 결정
`rag_search(query)`가 호출되면 내부적으로 (1) 질의어를 번역(`_translate`, 한국어면 영어로 / 영어면 한국어로)하고, (2) 원본과 번역본 **둘 다**로 벡터 검색을 수행한 뒤, (3) 최상위 유사도가 더 높은 쪽 결과를 채택합니다. 호출자(에이전트)는 질문이 어느 언어인지 미리 판단하거나 전달할 필요가 없습니다.

## 결과/트레이드오프
- **장점**: 에이전트/클라이언트가 언어를 몰라도 되므로 시스템 프롬프트나 API 계약이 단순해집니다. 실제로 초기에는 `chat.html`이 정규식으로 언어를 판단해 `is_korean` 플래그를 서버에 넘기는 방식이었는데, "HTML이 언어를 몰라도 되게 해달라"는 요구로 이 설계로 옮겨왔습니다.
- **단점(비용)**: 매 `rag_search` 호출마다 번역 LLM 호출 1회 + 벡터 검색 2회가 발생해, 언어가 하나로 고정된 경우보다 지연 시간과 Bedrock 호출 비용이 늘어납니다. 실측으로도 `rag_search` 도구 실행에만 5초 이상 걸리는 사례가 있었습니다(성능 분석은 [0008](0008-performance-instrumentation.md) 참고).
- **알려진 한계**: 번역 프롬프트가 고유명사(페이지 제목, 시스템명, 이슈 트래커 이름 등)를 그대로 보존하도록 명시하지 않고 있어서, 한국어와 영문 고유명사가 섞인 질문(예: "HowToCommit 페이지에서 JIRA 이슈 ID를 어디에 넣어요?")에서 번역이 고유명사를 훼손할 잠재적 위험이 있습니다. 다만 원본 질의어도 항상 함께 검색하므로 최악의 경우에도 번역만 하고 원본을 버리는 설계보다는 안전합니다. 아직 실측된 문제는 아니라 코드를 더 복잡하게 만들지 않고 관찰 중입니다(`data/documents/ISSUES.md` 1절).
