# 0004. Multi-Agent Supervisor 대신 단일 에이전트 유지

- 상태: 채택 (스코프 판단)
- 관련 코드: `src/agent/agent.py`
- 관련 문서: `data/documents/ISSUES.md` 3절

## 맥락
이 저장소 day6~7은 `langgraph_supervisor.create_supervisor`로 여러 전문 에이전트(RAG 담당, MCP 도구 담당, 잡담 담당)를 슈퍼바이저가 라우팅하는 패턴을 다룹니다. 이 프로젝트도 같은 패턴을 그대로 가져올 수 있었지만, 실제로 쓸 도구는 `rag_search`/`get_page`/`search_confluence` 세 개뿐이라 여러 에이전트로 쪼갤 만한 이유가 뚜렷하지 않았습니다.

## 결정
슈퍼바이저 없이 단일 ReAct 에이전트(`create_agent`)에 세 도구를 모두 등록하는 구조를 유지합니다([0001](0001-rag-mcp-hybrid-single-agent.md)). Day5의 가드레일/HITL/미들웨어 패턴도 같은 이유(범위 대비 실익이 낮음)로 그대로 적용하지 않았고, 대신 목적이 겹치는 부분(실패 시 대체 경로로 재시도)만 모델 폴백 체인([0003](0003-model-fallback-chain.md))으로 자체 구현했습니다.

## 결과/트레이드오프
- **장점**: 슈퍼바이저 계층, 라우팅 규칙, 에이전트 간 핸드오프를 설계·디버깅할 필요가 없어 1.5일 규모의 구현에 적합했습니다. 도구가 3개뿐인 지금 규모에서 "tool 과잉"(도구가 많아 모델이 잘못 고르는 문제)도 실질적으로 겪지 않았습니다.
- **단점**: 이 판단은 "지금 도구가 3개"라는 현재 규모에 근거한 것이라, 도구가 늘어나거나(수십 개 이상) 성격이 크게 갈리는 시스템(예: HR/자산관리/코드리뷰 등 이질적인 도메인)을 추가로 다뤄야 하면 재검토가 필요합니다.
- **재검토 기준**: `ISSUES.md` 3절에 정리한 대로, 도구가 많아질 때의 실제 해법은 MCP 여부가 아니라 (1) 도구 큐레이션 → (2) 멀티 에이전트 라우팅 → (3) 동적 도구 선택(tool retrieval) 순으로 검토하는 것이 맞습니다. 지금은 1단계(큐레이션: 컨플루언스 REST 엔드포인트 수십 개를 `get_page`/`search_confluence` 두 개로 추림)만으로 충분했습니다.
