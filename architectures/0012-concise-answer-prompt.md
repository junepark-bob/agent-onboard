# 0012. 최종 답변을 간결하게 쓰도록 유도 — output 토큰 축소로 응답 시간 절감

- 상태: 채택
- 관련 코드: `src/agent/agent.py`(`SYSTEM_PROMPT`, `MAX_OUTPUT_TOKENS`, `build_agent()`)
- 선행 문서: [0008](0008-performance-instrumentation.md), [0011](0011-performance-optimization-round.md)

## 맥락
[0011](0011-performance-optimization-round.md)의 인프라 최적화(중복 실행 제거, 재시도 축소, 캐싱) 이후에도 에이전트 본체의 추론 시간(`llm_ms`) 자체는 줄지 않았다. "턴이 진행될수록 각 턴이 느려진다"는 현상([0008](0008-performance-instrumentation.md)의 MCP 검증에서 처음 관찰)의 원인이 입력(누적된 컨텍스트) 때문인지 출력(생성하는 텍스트 양) 때문인지 불분명했다.

## 원인 진단
Bedrock Converse API가 턴마다 돌려주는 `usage_metadata`(input_tokens/output_tokens)를 직접 읽어 확인했다. 같은 요청 안의 두 턴(turn1: 2854.1ms/input 2164/output 245, turn2: 5364.5ms/input 3134/output 647)을 비교했을 때, 시간 차이를 **input 토큰만으로 설명하면 고정 오버헤드가 음수(-2746ms)**가 나와 성립하지 않았고, **output 토큰만으로 설명하면 토큰당 ~6.2ms + 고정 오버헤드 ~1324ms로 말이 되는 값**이 나왔다. 즉 이 프로젝트의 턴별 지연은 입력(컨텍스트) 증가보다 **출력 생성량**이 더 지배적인 원인이었다.

## 검토한 대안과 실측 결과
1. **RAG 청크 크기/오버랩 축소(1000/150 → 300/50)**: 사용자가 처음 제안했으나, (a) 이건 입력 쪽을 줄이는 방법이라 위 진단(출력이 더 지배적)과 어긋나고, (b) 검색 정확도를 직접 해칠 위험(청크가 작아지면 임베딩 신호가 줄고, 문장이 끊길 수 있음)이 있어 보류했다.
2. **`max_tokens` 하드 컷오프**: 700으로는 자연 답변 길이(454토큰)보다 여유로워 아무 효과가 없었다. 250까지 낮추자 turn2가 25.4% 빨라졌지만(3669.8ms → 2738.0ms), **답변이 "...나중에 댓글에 추가해야"처럼 문장 중간에서 그대로 잘렸다** — 사용자에게 미완성 답변을 보여주게 되어 채택할 수 없었다.
3. **시스템 프롬프트로 간결한 완결된 답변 유도 + `max_tokens`는 안전망으로만 사용**(최종 채택): "답변은 간결하게 써라 — 출처 링크가 있으니 본문에 원문을 길게 옮기거나 장황하게 나열하지 마라. 다만 질문이 요구하는 구체적인 수치·이름·조건은 절대 생략하지 마라. 답변은 완결된 문장으로 끝나야 한다"를 `SYSTEM_PROMPT`에 추가하고, `max_tokens=1000`(자연 답변 길이보다 훨씬 넉넉해 정상적으로는 절대 안 닿는 값)을 안전망으로만 걸었다.

## 실측 결과 (같은 질문, 같은 모델 Nova Pro, 표본 2개씩)

| | 기준(캡 없음, 기존 프롬프트) | 간결 프롬프트 + `max_tokens=1000` |
|---|---|---|
| turn2(최종 답변 턴) 평균 | 4229.1ms | 4074.75ms (-3.6%) |
| output 토큰 평균 | 510.5 | 384 (**-24.8%**) |
| 전체 wall 시간 평균 | 7648.95ms | 6901.95ms (**-9.8%**) |
| 답변 완결 여부 | 완결 | 완결 |

표본 1개만 봤을 때는 turn2가 오히려 느려 보이는 결과가 한 번 나왔는데(자연스러운 Bedrock API 호출별 지연 변동 때문으로 추정), 표본을 하나 더 모아 평균을 내자 방향이 명확해졌다. 간결 프롬프트 쪽 output 토큰은 두 표본 모두 정확히 384로 매우 일관됐던 반면(temperature=0에서 지침이 답변 길이를 안정적으로 수렴시키는 것으로 보임), 기준 쪽은 454/567로 변동폭이 더 컸다.

## 결정
`agent.py`의 `SYSTEM_PROMPT`에 간결한 답변 지침을 추가하고, `build_agent()`의 `ChatBedrockConverse`에 `max_tokens=1000`(자연 답변을 자르지 않는 넉넉한 안전망)을 설정했다.

## 결과/트레이드오프
- **장점**: output 토큰이 안정적으로 ~25% 줄었고, 전체 응답 시간도 ~10% 개선됐다. `max_tokens`를 하드 컷오프로 직접 쓰는 것과 달리 답변이 잘리지 않는다.
- **회귀 위험(미확인)**: 이번 검증은 질문 하나로만 했다. `evaluation/test_queries.csv`의 `expected_traits` 중 "여러 문서 내용을 각각 반영"처럼 상세한 나열을 요구하는 케이스(#14 등)가 간결화 지침 때문에 필요한 세부 내용을 빠뜨려 점수가 떨어지지 않는지, 평가셋 전체 재실행으로 아직 확인하지 못했다. 다음 라운드에서 확인이 필요하다.
- **답변 내용의 실행별 변동은 이번 변경과 무관하게 원래 있었다**: 실측 과정에서 같은 질문의 서로 다른 실행이 문서의 다른 부분(이슈 이름 규칙 vs 커밋 검토 절차)을 인용하는 걸 관찰했다 — `rag_search`가 매번 정확히 같은 청크를 상위로 뽑는다는 보장이 없어서 생기는 현상이며, 이번 프롬프트 변경이 유발한 문제가 아니다.
- **RAG 청크 크기 조정은 여전히 보류 상태**: 이번 진단(출력이 더 지배적)으로 우선순위가 낮아졌지만, 완전히 기각된 건 아니다. 필요해지면 기존 `chroma_db`를 직접 덮어쓰지 말고 별도 컬렉션으로 만들어 평가셋으로 나란히 비교하는 방식을 권장한다.

## 실서버 최종 확인: 세션 최초 측정 대비 누적 효과
이 프롬프트를 실제 서버 코드에 반영한 뒤, `performance_trace.jsonl`에 세션 최초 측정(1라인, 어떤 조치도 적용하기 전)과 **완전히 같은 질문**으로 실제 `/query` 요청 결과가 쌓였다(8라인). 둘 다 쓰로틀링이 없었던 깨끗한 비교라, [0009](0009-english-only-domain-language-policy.md)/[0011](0011-performance-optimization-round.md)/이 문서의 조치를 모두 합친 누적 효과를 볼 수 있다.

| 지표 | 1라인(최초, 조치 전) | 8라인(전체 조치 적용 후) | 변화 |
|---|---|---|---|
| `total_ms` | 33132.5 | 7391.9 | **-77.7%** (4.5배) |
| `mcp_setup_ms` | 2234.6 | 0.0 | -100% |
| `rag_ms` | 5322.7 | 1225.6 | -77.0% |
| `llm_ms` | 19314.8 | 5867.7 | -69.6% |
| 미계측 구간 비중 | 19% | 4% | rag_search 중복 실행 제거의 부수 효과 |

`llm_ms`의 -69.6%는 이 문서의 간결 프롬프트 효과뿐 아니라, 이번엔 쓰로틀링이 전혀 없었다는 운(`llm_failed_ms: 0`)과 실제로 어떤 모델이 응답했는지가 섞인 결과라 이 문서의 조치만으로 낸 순수 수치는 아니다 — 표본도 각 1개씩이라 재현성 확인은 더 필요하다. 그래도 `mcp_setup_ms`/`rag_ms`처럼 코드로 통제되는 지표는 안정적으로 유지될 것으로 본다.

### 8라인을 이용한 더 정밀한 검증 (모델 고정)
사용자가 8라인은 `us.amazon.nova-pro-v1:0`으로 직접 실행했다고 알려줬다(실행 후 `models.py`는 원래 폴백 목록으로 원복). 이 정보로 위 "검토한 대안과 실측 결과" 절의 Nova Pro 통제 비교와 **모델을 고정한 채로** 직접 비교할 수 있다.

| | turn1+turn2 합계 (`llm_ms`) |
|---|---|
| 기존 프롬프트(캡 없음) 표본 평균 | 6414.15ms |
| 8라인(간결 프롬프트, 실서버) | 5867.7ms |

8라인은 기존 프롬프트 평균보다 **-8.5%** — 위 표의 "전체 wall 시간 -9.8%"와 거의 정확히 일치한다. 즉 간결 프롬프트의 실제 기여분은 한 자릿수 %대가 맞고, 1라인 대비 -69.6%라는 수치를 이 프롬프트만의 효과로 해석하면 안 된다(모델 차이·쓰로틀링 유무가 대부분을 차지한다). 아래 "7라인과 비교" 절도 같은 이유로 재해석이 필요하다.

### 7라인과 비교 시 주의: 모델이 다르다
`performance_trace.jsonl` 7라인(하이쿠 하드코딩, 이 문서의 조치 적용 전)과 8라인(Nova Pro, 이 문서의 조치 적용 후)을 비교하면 `llm_ms`가 13084.8ms → 5867.7ms(-55.2%)로 크게 줄어든 것처럼 보이지만, 이건 **서로 다른 모델을 비교한 것**이라 그 차이를 이 문서의 프롬프트 변경 효과로 돌리면 안 된다. 같은 모델(Nova Pro) 안에서의 순수 효과는 위 "-8.5%"가 더 정확한 수치다.
