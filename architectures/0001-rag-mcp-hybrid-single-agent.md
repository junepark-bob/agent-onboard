# 0001. RAG + MCP 하이브리드를 단일 ReAct 에이전트로 구성

- 상태: 채택
- 관련 코드: `src/agent/agent.py`, `src/agent/retriever.py`, `src/agent/tools.py`

## 맥락
온보딩 신입이 컨플루언스에서 답을 못 찾는 문제를 풀려면, 사전에 크롤링해둔 문서(빠르고 저렴하지만 최신화가 느림)와 컨플루언스 실시간 조회(항상 최신이지만 매번 API 호출)를 둘 다 다뤄야 합니다. 이 둘을 언제 쓸지 결정하는 로직을 어디에 둘지가 첫 번째 갈림길이었습니다: (a) 고정된 그래프 분기(예: "유사도가 X 미만이면 무조건 실시간 검색으로 폴백")로 강제할지, (b) 하나의 에이전트에게 두 가지 도구를 다 쥐여주고 스스로 판단하게 할지.

## 결정
`rag_search`(로컬 RAG), `get_page`/`search_confluence`(MCP를 통한 실시간 조회/검색) 세 도구를 모두 하나의 `create_agent`(ReAct) 인스턴스에 등록하고, 어떤 순서로 무엇을 부를지는 시스템 프롬프트로만 안내합니다("먼저 rag_search로 검색하고, 결과가 부족하면 search_confluence로 실시간 검색하라"). 고정된 LangGraph 분기 그래프는 만들지 않았습니다.

## 결과/트레이드오프
- **장점**: 도구가 3개뿐인 규모에서는 별도 분기 그래프를 설계·유지보수하는 비용보다, 에이전트가 스스로 판단하게 하는 쪽이 구현이 단순합니다. 애매한 경계(유사도가 임계값에 걸쳐 있는 경우 등)에서도 코드로 명시적 규칙을 다 나열할 필요가 없습니다.
- **단점**: 에이전트의 판단은 결정적(deterministic)이지 않습니다 — 같은 질문에도 매번 정확히 같은 순서로 도구를 부른다는 보장이 없고, 프롬프트 지침을 따르지 않을 잠재적 위험이 있습니다. 실제로 이 위험 때문에 "검색으로 못 찾은 내용은 사전 지식으로 채우지 말라"는 안전장치를 프롬프트에만 의존하지 않고 도구 코드 자체(스페이스 스코프 강제, [0005](0005-mcp-tool-scope-enforcement.md) 참고)에도 둬야 했습니다.
- 도구 수가 늘어나거나(수십 개 이상) 성격이 크게 갈리면(예: HR 시스템 vs 코드 저장소), 이 저장소 day6/day7의 `langgraph_supervisor` 패턴처럼 여러 전문 에이전트로 분리하는 재검토가 필요합니다 ([0004](0004-single-agent-not-supervisor.md) 참고).
