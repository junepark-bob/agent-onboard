# 0009. 대상 도메인이 전부 영어라는 특성에 맞춘 언어 정책 단순화

- 상태: 채택
- 관련 코드: `src/agent/retriever.py`(`rag_search`, `translate`, `_is_korean`), `src/agent/agent.py`(`SYSTEM_PROMPT`), `src/server/server.py`(`POST /translate`), `static/chat.html`
- 선행 문서: [0002](0002-bilingual-rag-search.md)(이중 언어 검색), [0008](0008-performance-instrumentation.md)(성능 계측으로 병목 확인)

## 맥락
[0008](0008-performance-instrumentation.md)에서 질의 하나에 33초가 걸리는 걸 실측했고, 그중 RAG 도구 실행(16%)의 원인이 [0002](0002-bilingual-rag-search.md)의 "원문 질의와 번역본을 항상 둘 다 검색해서 더 높은 쪽을 채택"하는 이중 검색 설계였습니다. 그런데 이 프로젝트가 다루는 대상은 애초에 **도메인 자체가 전부 영어로 고정**돼 있습니다 — 크롤링 대상(Apache Hadoop HADOOP2 스페이스)의 모든 문서가 영어이고, 실무로 교체되더라도 이 서비스가 겨냥하는 "컨플루언스 문서"라는 도메인 자체가 한국 SI/SM 프로젝트라 해도 대개 기술 문서는 영어로 작성되는 경우가 많습니다. 즉 "질의어가 어느 언어든 둘 다 검색해서 안전하게 커버한다"는 범용적 설계는, 문서가 전부 영어라는 이 도메인의 실제 특성 앞에서는 항상 절반이 낭비되는 비용이었습니다(한국어 원문 검색은 실측 top1 유사도 ~0.13으로 사실상 항상 지고, 영어 질의의 한국어 번역본 검색도 이길 일이 없습니다).

같은 맥락에서, 최종 답변을 "질문 언어와 무관하게 항상 한국어로 강제 번역"하던 기존 정책([0002](0002-bilingual-rag-search.md) 도입 당시의 요구사항)도 재검토했습니다. 이 강제 번역은 매 요청마다 추가 비용 없이 모델이 알아서 처리하고 있었지만(별도 번역 호출이 있던 건 아님), 정책 자체가 "질문이 영어여도 무조건 한국어로 답하라"는 지시였기 때문에 사용자가 영어 답변을 그대로 원하는 경우에도 선택권이 없었습니다.

## 결정
1. **RAG 검색은 항상 영어로만 한다.** `rag_search()`가 질의어에 한글이 하나라도 있으면(`_is_korean`, 정규식 기반 결정적 판단) 영어로 번역한 뒤 그 번역본 하나만 검색하고, 이미 영어면 번역 없이 그대로 검색한다. 원문/번역본을 둘 다 검색해서 비교하는 로직은 제거했다.
2. **최종 답변은 질문과 같은 언어로 자연스럽게 쓰고, 답변을 생성한 뒤 다시 강제로 번역하지 않는다.** `SYSTEM_PROMPT`에서 "무조건 한국어로만 답하라"는 지시를 "질문과 같은 언어로 답하라"로 바꿨다. 영어로 질문하면 영어로 답이 나올 수 있다.
3. **번역이 필요하면 사용자가 채팅 UI에서 직접 요청한다.** `POST /translate`(새 엔드포인트, `retriever.translate()` 재사용)를 추가하고, `chat.html`은 답변에 한글이 하나도 없으면(`containsKorean` 휴리스틱) "한국어로 보기" 버튼을 답변 아래에 표시해, 클릭했을 때만 번역을 요청하도록 했다.

## 결과/트레이드오프
- **성능**: 영어 질의는 번역 호출과 두 번째 벡터 검색이 통째로 사라져 `rag_search` 실행 시간이 실측 기준 5초대에서 1초대로 줄었다(한국어 질의는 번역 1회 + 검색 1회로, 기존 대비 검색 횟수가 절반으로 줄었다). 답변을 항상 한국어로 강제하지 않게 되면서, 사용자가 번역이 필요 없다고 판단하면(예: 영어에 익숙한 사용자, 또는 원문 그대로 확인하고 싶은 경우) 그만큼의 응답 자체는 그대로 받고 번역 왕복은 아예 생략할 수 있다.
- **트레이드오프**: 온보딩 신입이 한국어 사용자라는 원래 가정([0002](0002-bilingual-rag-search.md) 도입 배경)을 생각하면, 영어로 질문했을 때 답도 영어로 나오는 건 일부 사용자에게는 불편할 수 있다. "한국어로 보기" 버튼이 이를 보완하지만, 번역 결과를 보려면 클릭 한 번과 추가 왕복(별도 LLM 호출)이 필요해 완전히 무비용은 아니다 — 다만 이 비용을 "필요한 사람만 지불"하도록 옮긴 것이 이번 결정의 핵심이다.
- **일반화 가능성에 대한 솔직한 평가**: 이 결정은 "이 프로젝트의 대상 문서가 전부 영어"라는 현재 도메인 특성에 근거한 것이다. 만약 대상 컨플루언스가 다국어 문서를 섞어 쓰는 조직(예: 한국어 회의록 + 영어 기술 문서가 공존)으로 바뀌면, "검색은 항상 영어로만"이라는 가정이 깨지므로 이 ADR의 전제부터 재검토해야 한다.
- **회귀 영향 확인**: `evaluation/test_queries.csv`(20건)와 `evaluation/test_self_queries.csv`(11건)는 모두 한국어로 작성된 질문이라, "질문과 같은 언어로 답한다"는 새 정책 아래에서도 여전히 한국어 답변이 기대되므로 기존 평가 결과에 영향이 없음을 확인했다. 영어 질문에 대한 회귀 확인은 과거 버그 재현에 썼던 질문("In the Chukwa data flow, where does the Agent first write data to?")으로 직접 재검증했다 — 이제는 의도대로 영어 답변이 나온다.
