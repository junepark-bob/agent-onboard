# 0010. 라우터 패턴: 번역 백엔드를 Bedrock LLM과 로컬 전용 모델 중 선택 가능하게 분리

- 상태: 채택
- 관련 코드: `src/agent/translator.py`(신규), `src/agent/retriever.py`, `src/agent/__init__.py`
- 선행 문서: [0002](0002-bilingual-rag-search.md), [0009](0009-english-only-domain-language-policy.md)

## 맥락
[0002](0002-bilingual-rag-search.md)/[0009](0009-english-only-domain-language-policy.md)에서 번역(`translate()`)은 지금까지 `MODEL_CANDIDATES` 폴백 체인을 통한 Bedrock 범용 LLM 호출로 구현돼 있었다. 번역은 규칙이 비교적 명확한 단순 작업인데도, 복잡한 추론이 필요한 에이전트 본체와 똑같은 무거운 모델 체인을 타고 있었다. 라우터(Router) 패턴 — 단순한 작업은 가벼운 전용 경로로 즉시 처리하고, 정말 필요한 경우에만 무거운 경로를 타게 하는 설계 — 관점에서, 번역을 에이전트의 Bedrock 모델 폴백 체인에서 분리해 별도의 경량 전용 모델로 처리하도록 바꿨다.

## 검토한 대안과 실측 결과
1. **Amazon Translate(AWS 전용 번역 서비스)**: 가장 먼저 시도했으나, 현재 IAM 사용자에게 `translate:TranslateText` 권한이 없어 `AccessDeniedException`으로 즉시 막혔다. 권한 추가는 AWS 콘솔 작업이 필요해 이번 범위에서는 보류했다.
2. **로컬 Hugging Face 번역 모델을 내장**(최종 채택): 네트워크/Bedrock 쿼터에 전혀 의존하지 않기 위해, `Helsinki-NLP/opus-mt-ko-en`(한→영 전용 MarianMT) 먼저 시도했으나 실제 평가 문항으로 테스트한 결과 도메인 고유명사를 자주 오역했다("하둡"→"deep-frequency", "Chukwa"→"Tukwa", "Agent"→"Agen"). 영→한 방향으로 검토한 `Helsinki-NLP/opus-mt-tc-big-en-ko`는 아예 알아볼 수 없는 문장("process、grad、블로그 마음 well。.")을 뱉어 사용 불가 판정했다. 최종적으로 `facebook/nllb-200-distilled-600M`(양방향 단일 모델)로 교체했다 — 이 모델은 Chukwa/JIRA/HowToCommit 등 **영문 표기로 쓰인** 고유명사는 잘 보존했다.

## 실측으로 드러난 더 심각한 문제: 한글 음차 외래어 오역
`test_queries.csv`/`test_self_queries.csv`의 한국어 질문 13건 전체로 NLLB를 테스트한 결과, 영문 표기 고유명사는 문제없이 보존됐지만 **한글로 음차된 외래어**를 완전히 다른 뜻으로 오역하는 사례가 13건 중 2건 나왔다:
- "커미터"(committer) → "comic book artist"
- "우분투"(Ubuntu) → "Wrestling"

이 둘은 기존 Bedrock LLM 기반 번역에서는 겪지 않던 문제였다. 처음 제안했던 "영문 표기 고유명사를 정규식으로 찾아 플레이스홀더로 치환 후 번역·복원"하는 보호-번역-복원 방식을 실제로 구현해 테스트했지만, **오히려 역효과**였다 — NLLB가 플레이스홀더(`<K0>` 등)를 생성 과정에서 통째로 누락하거나 변형시켜서, 원래 잘 번역되던 Chukwa/JIRA/HowToCommit 사례까지 망가뜨렸다. 근본적으로 "커미터"/"우분투"/"하둡" 같은 한글 음차어는 애초에 영문 표기가 아니므로 이 정규식 기반 보호 방식으로는 애초에 잡히지도 않는다.

## 결정
정규식 기반 보호-복원 대신, 이 도메인(Apache Hadoop 생태계)에서 실제로 오역이 확인됐거나 자주 쓰이는 한글 음차어를 **번역 전에 사전(GLOSSARY)으로 원어(영문)로 미리 치환**하는 방식을 채택했다(`translator.py`의 `GLOSSARY` 딕셔너리: 하둡/커미터/우분투/지라/컨플루언스/카프카/스파크/자바/메이븐/깃허브). 이 방식은 해당 사전에 등록된 단어에 대해서는 모델이 아예 오역할 기회 자체를 없앤다.

로컬 모델의 실측 결과(정확성 개선은 있지만 속도 이득은 없고, 아래 "후속 발견"의 콜드스타트 변동성까지 있음)를 종합해, **로컬 모델을 유일한 경로로 강제하지 않고 `TRANSLATION_BACKEND` 환경 변수(`bedrock`(기본값) | `local`)로 선택 가능**하게 바꿨다. 지금까지 가장 많이 검증된 Bedrock 경로를 기본값으로 유지하고, 로컬 모델은 Bedrock 쿼터 독립성이 필요할 때 켜는 옵션으로 둔다. 기본값이 `bedrock`이므로, `torch`/`transformers`와 NLLB 모델 로드는 `TRANSLATION_BACKEND=local`을 명시할 때만 지연 로딩(lazy import)되고, 그 외에는 아예 건드리지 않는다.

## 결과/트레이드오프
- **정확성**: 실측으로 확인된 두 오역 사례(커미터/우분투)와 합성 테스트의 하둡 사례가 모두 글로서리 적용 후 정상 번역되는 것을 확인했다.
- **속도**: 정직하게 말하면, 성공적인 호출 기준으로는 **속도 차이가 거의 없다** — 같은 질문으로 실측한 `rag_search` 개별 호출 시간이 Bedrock 기반(1167~1183ms)과 로컬 NLLB 기반(1111~1222ms)이 사실상 동일했다. `rag_search`가 5초대에서 1초대로 줄어든 건 [0009](0009-english-only-domain-language-policy.md)의 이중 검색 폐지 덕분이었지, 이번 로컬 모델 교체의 효과가 아니다.
- **진짜 얻은 것은 Bedrock 쿼터로부터의 독립성**: 이 세션 내내 겪은 "Too many tokens per day" 쓰로틀링([0008](0008-performance-instrumentation.md) 참고)은 에이전트 본체(Sonnet 등)의 Bedrock 호출에서 발생하는 문제이고, 번역을 로컬 모델로 옮겨도 그 부분은 줄지 않는다. 다만 번역 자체는 이제 Bedrock 쿼터/네트워크와 완전히 무관해져서, 쿼터가 얼마나 소진되든 번역만큼은 항상 일정한 속도로 동작한다.
- **새 의존성 비용**: `torch`(CPU 전용, ~126MB) + `transformers` + `sentencepiece`/`sacremoses`를 공유 루트 `.venv`에 추가로 설치했다. 모델(NLLB-200-distilled-600M) 로드는 프로세스당 1회(실측 14~32초)만 치르면 되므로(서버 프로세스라면 기동 시 한 번), 매 요청마다 드는 비용은 아니다.
- **글로서리의 근본적 한계**: 이 방식은 **사전에 등록한 단어에만** 적용된다. 등록되지 않은 새로운 한글 음차 외래어가 나오면 여전히 오역될 수 있다 — 완전히 일반적인 해법이 아니라, 도메인 어휘가 비교적 고정돼 있는(Apache Hadoop 생태계) 이 프로젝트 규모이기 때문에 실용적으로 성립하는 절충안이다. 새 용어에서 오역이 발견되면 `GLOSSARY`에 추가하는 방식으로 대응한다.
- **Amazon Translate 재검토 여지**: IAM 권한이 추가되면 Amazon Translate(진짜 전용 번역 서비스, LLM도 로컬 모델도 아님)로 다시 교체하는 것도 검토할 만하다 — 다만 그 경우에도 고유명사 처리 정확도를 별도로 재검증해야 한다.

## 후속 발견: `llm_ms`에 대한 오해, 그리고 로컬 모델의 콜드스타트 변동성
로컬 모델 적용 후 `performance_trace.jsonl`에서 `rag_ms`뿐 아니라 `llm_ms`까지 늘어난 사례가 나와서, "번역을 Bedrock으로 안 하면 `llm_ms`도 줄어야 하는 것 아니냐"는 질문이 나왔다. 확인해보니 이건 처음부터 성립하지 않는 기대였다.

- **`llm_ms`는 애초에 번역 시간을 포함한 적이 없다.** `PerformanceTracker`(`architectures/0008-performance-instrumentation.md`)의 `llm_ms`는 에이전트 본체(도구 선택·최종 답 작성을 담당하는 `ChatBedrockConverse`)의 호출만 잡는다. 번역은 `rag_search` **도구 내부**에서 일어나므로, 백엔드가 Bedrock이든 로컬 모델이든 항상 `rag_ms`(도구 실행 시간)에만 반영되고 `llm_ms`에는 절대 포함되지 않는다. 실제로 `llm_ms`가 늘어난 원인은 번역과 무관하게 그 시점에 `llm_failed_ms`(쓰로틀링 재시도로 날린 시간)가 14.9초 → 29.5초로 더 커진 것이었다 — 세션 내내 Bedrock 일일 토큰 쿼터가 계속 소진되면서 에이전트 본체가 더 아래 후보 모델로 폴백하는 빈도가 늘어난 결과다.
- **`rag_ms`가 5847.1ms까지 늘어난 것은 로컬 모델의 콜드스타트 변동성으로 보인다.** 같은 프로세스에서 반복 호출하면 `rag_search` 개별 호출은 1.1~1.2초로 안정적이지만(Bedrock과 비슷한 수준, 위 "결과/트레이드오프" 참고), 프로세스를 새로 시작한 직후의 첫 추론 호출은 3.7초까지 걸린 사례도 있었다. Bedrock은 AWS 쪽에 모델이 항상 로드돼 있는 원격 API라 호출마다 균일하지만, 로컬 모델은 프로세스 시작 후 첫 `.generate()` 호출에서 PyTorch 내부 스레드풀/커널 초기화 비용이 붙어 지연이 들쭉날쭉하다. 이는 로컬 백엔드가 감수해야 하는 진짜 트레이드오프로, "성공 호출 기준 속도 차이 없음"이라는 위 결론에 "다만 프로세스 시작 직후 첫 호출은 예외"라는 단서를 추가한다.

**결론**: 두 지표의 증가 모두 번역 백엔드 전환이 "느리게 만든" 것이 아니다. `llm_ms` 증가는 Bedrock 쿼터 소진(번역과 무관), `rag_ms` 증가는 로컬 모델 특유의 콜드스타트 변동성(정상 상태에서는 Bedrock과 동등)이다.
