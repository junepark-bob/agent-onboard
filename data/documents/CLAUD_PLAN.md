# 컨플루언스 온보딩 Agent — 기획 종합 (SERVICE.md 초안 작성 전 단계)

## Context

AX 교육 마지막 과정으로 0.5일 기획 + 1.5일 미니 프로젝트 개발을 진행 중이다. 미니 프로젝트는 "SI/SM 프로젝트에 온보딩하는 신입 멤버"를 위해 컨플루언스와 상호작용하는 AI 에이전트를 만드는 것으로, `plans/ideas.md`에 초안 아이디어가 있었다. 오늘 완성해야 할 산출물은 `SERVICE.md`, `test_queries.csv`(최소 10건), 최소 파이프라인 스케치다.

`ideas.md`의 초안은 "컨플루언스 MCP로 공개 API 호출"만 언급했지만, `mini-pjt/CLAUDE.md`의 폴더 규약은 `src/tools.py`(도메인 도구)와 `src/retriever.py`(RAG 파이프라인)를 별도로 요구한다. 또한 실제 페인포인트(사내 방화벽/보안 설정 등)와 테스트 대상(ASF 공개 컨플루언스)의 문서 내용이 근본적으로 다르다는 간극이 있었다. 소크라테스 질문법으로 이 간극들을 메우고 요구사항을 구체화한 결과를 아래에 종합한다.

## 확정된 결정 사항

### 사용자 규모 / 운영 단위
- 연간/분기별 대략 **10~50명**의 신입이 새 SI/SM 프로젝트에 투입되는 중규모 조직 기준.
- 운영은 **PoC 단계에서는 프로젝트마다 개별 인스턴스**로 두고, 효과가 검증되면 회사 전체가 공유하는 하나의 서비스로 확장하는 2단계 전략.

### 현재 방식 (As-Is)
- 지금은 신입이 막히면 **사수/멘토에게 메신저로 질문**하며, 응답 자체는 즉시~5분 이내로 빠른 편.
- 즉, 페인포인트는 "답을 얻는 속도"가 아니라 **매번 다른 사람의 업무를 끊고(인터럽트) 물어봐야 한다는 것과 셀프서비스가 안 된다는 것**. SERVICE.md 배경 섹션에서 이 뉘앙스를 반영해야 함 (단순 "느려서 문제"가 아님).

### 검증 목표
- 실제 온보딩 페인포인트를 있는 그대로 재현하기보다, **MCP + RAG + 에이전트 파이프라인 아키텍처 자체가 동작하는지 검증**하는 것이 1.5일 개발의 우선순위.
- ASF 공개 컨플루언스는 실무 컨플루언스로 교체 가능한 구조를 검증하기 위한 스탠드인 데이터로 취급한다.

### 대상 스페이스
- **Apache Hadoop의 `HADOOP2` 공간** (`cwiki.apache.org/confluence/display/HADOOP2`) 사용.
- 인증 없이 REST API 접근 가능함을 확인함 (`/confluence/rest/api/content?spaceKey=HADOOP2` 정상 응답).
- `HowToSetupYourDevelopmentEnvironment`, `HowToContribute`, `HowToCommit`, `HowToCodeReview`, `HowToRelease` 등 온보딩 매뉴얼과 유사한 문서들이 존재.
- 레거시/마이그레이션 공지가 있는 공간이라 내용이 잘 바뀌지 않음 → 평가 재현성 측면에서 오히려 유리.

### 검색 아키텍처 (src/retriever.py vs src/tools.py 역할 분담)
- **`retriever.py` (RAG)**: HADOOP2에서 온보딩 관련 핵심 페이지 **20~30개만 선별 크롤링**해 `data/`에 저장하고 chroma_db로 임베딩, 의미 검색 수행. day2/day6/day7의 기존 RAG 패턴과 동일.
- **`tools.py` (MCP)**: Confluence REST API를 감싸는 자체 MCP 서버(day4~7의 `mcp_server.py` 패턴)로 두 가지 도구 제공:
  1. 특정 페이지 ID/URL로 최신 원문 조회
  2. CQL 기반 실시간 검색 (사전 크롤링되지 않은 문서도 찾기 위한 폴백)
- Confluence base URL / 인증 토큰은 **`.env`로 추상화**하여, 설정만 바꾸면 사내 컨플루언스로 교체 가능하게 설계 (루트 CLAUDE.md의 "비밀 값은 .env에서 읽는다" 규칙과도 일치).

### 폴백 로직 (모름 판정 포함)
- 순서: 로컬 RAG 검색 → (유사도 임계값 미달 시) 실시간 CQL 검색 → (그래도 없으면) "모른다"고 답변.
- 이 순서 판단은 **에이전트가 자율적으로 수행** (`langchain.agents.create_agent`로 만든 단일 ReAct 에이전트에 `rag_search`, `confluence_live_search`, `confluence_get_page` 세 도구를 모두 주고, 시스템 프롬프트로 "먼저 로컬, 부족하면 실시간" 순서만 지침). 고정 LangGraph 분기 그래프는 사용하지 않음.
- 실시간 CQL 검색이 타임아웃/장애 나면 **RAG 결과만으로 조용히 계속 진행** (trace에는 실패 기록, 사용자에게는 별도 에러 노출 안 함).
- 엄격한 응답 지연 목표는 두지 않음 (데모 수준으로 충분).

### 초기 구현 우선순위 (MVP vs 후순위)
- **1차(반드시 데모에서 동작)**: `retriever.py` RAG 검색 + 출처 인용 + 유사도 임계값 기반 "모름" 판단 + `trace` 기록. 이것만으로도 아키텍처 검증(핵심 가치)이 가능하다고 판단.
- **후순위(시간이 부족하면 가장 먼저 포기)**: `tools.py`의 실시간 CQL 검색(MCP 라이브 폴백). 페이지 단건 조회 도구보다도 우선 제외 대상.
- 즉 시간이 없으면 "RAG-only + 정직한 모름 답변"으로도 데모가 성립하고, 실시간 검색은 여유가 있을 때 추가하는 스트레치 목표.

### 응답 형식
- 요약 답변 + 출처 링크/원문 인용 필수.
- 관련 문서를 못 찾으면 "모른다"고 명시적으로 답변 (환각 방지).
- 대화는 **단일 턴**으로 충분 (멀티턴 메모리 불필요).

### API 계약 (mini-pjt/CLAUDE.md 규약)
- `POST /query`, `question` 필드 입력.
- 응답: `answer`, `contexts`, `trace` 세 키.
- `trace`는 day7 `local_tracer.py`/`trace.jsonl` 패턴처럼 **도구 호출 단계**(어떤 검색어로 RAG를 호출했는지, 문서 ID/유사도, MCP 호출 여부와 결과)를 기록.

### 재현성
- 에이전트/판정 모델 호출 시 **temperature=0 고정**.

### 사내 임팩트 / 수익화 관점
- **적용 범위**: 우리 회사(삼성SDS) 내부 전용 생산성 도구로 한정. 고객사 납품 상품화는 이번 범위 밖.
- **우선순위 임팩트 지표** (SERVICE.md 배경/목적 섹션에 반영):
  1. 신입 온보딩 소요 시간 단축 (최우선)
  2. 문서 자체의 최신화/품질 개선 유도 (에이전트가 못 찾은 질문을 로그로 남겨 문서 관리자에게 피드백)
  3. 프로젝트 투입 초기 리스크(설정 누락, 오작/버그) 감소
- **수익화 서술**: 별도 사업계획서 섹션은 만들지 않는다. SERVICE.md 배경 부분에 "온보딩 시간 단축 → 투입 인력의 생산 가능 시간 증가 → 비용 절감"이라는 **비용 절감 중심 ROI를 1~2문단으로 간단히만** 서술.

### 언어
- 한국어 신입 멤버가 영어 원문(HADOOP2) 문서를 다루는 상황을 가정.
- **요약/설명은 한국어**, **출처 인용구는 영어 원문 그대로** 남겨 번역 오류로 인한 정보 왜곡을 방지. LLM-judge의 출처 정확성 채점과도 정합.
- `test_queries.csv`의 `question` 컬럼도 **한국어**로 작성 (실제 사용자 관점과 일치).

### 크롤링 방식
- 하이퍼링크를 따라가는 자동 크롤러가 아니라, **사람이 직접 고른 20~30개 URL 리스트**를 수동 작성해두고, 스크립트로 그 리스트만 일괄 수집. 범위가 명확하고 품질이 예측 가능함.

### 평가 산출물 스키마
- `test_queries.csv` 컬럼: `question`, `category`(정상/범위밖), `expected_source_url`.
  - 정상 케이스: HADOOP2 문서로 답변 가능한 질문, 정답 출처 페이지 URL 명시.
  - 범위밖 케이스: 관련 문서가 없어 "모른다"로 응답해야 하는 질문.
  - 비율은 정상 7~8건 + 범위밖 2~3건 정도로 혼합.
- 평가 리포트: **질문별 점수 + 판정 사유**를 CSV/JSON으로 기록하고, 마지막에 전체 통계(평균 점수, 통과율) 요약.
- LLM-judge의 rubric 우선순위: **출처 정확성**을 최우선으로 채점 (인용 URL이 `expected_source_url`과 일치/포함하는지).

### 숫자 성공 기준
- LLM-judge 채점: **5점 만점**, 질문당 **평균 4점 이상**이면 그 질문은 성공.
- 전체 기준: `test_queries.csv` 10건 중 **7건(70%) 이상 통과**하면 오늘 산출물을 "성공"으로 판단.
