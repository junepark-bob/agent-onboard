# ISSUES.md — 설계 고민 1차 검토

기획/구현 중 나온 세 가지 고민에 대한 1차 검토와 해결책 제안이다. 현재 MVP 범위에 바로 반영할 것과, 나중에(스케일업 시) 고려할 것을 구분했다.

## 1. 혼합 언어(한글+영문 고유명사) 질의가 번역 기반 이중 검색에 미치는 영향

### 현재 구조
`src/retriever.py`의 `rag_search()`는 질의어를 번역(`_translate`)해서 원본과 번역본 둘 다로 벡터 검색을 하고, 최상위 유사도가 더 높은 쪽을 채택한다. 이는 "질문이 한국어인지 영어인지"를 완벽히 이분법으로 가정한 설계다.

### 검토
실제로는 "HowToCommit 페이지에서 JIRA 이슈 ID를 어디에 넣어요?"처럼 한 문장 안에 한국어와 영문 고유명사(페이지명, 시스템명, 코드 식별자)가 섞이는 경우가 흔할 것이다. 이때 걱정되는 실패 시나리오는 두 가지다.

1. **번역기가 고유명사를 오염시키는 경우**: `_translate()`가 "JIRA"를 "지라"로 음차하거나 "HowToCommit"을 의역해버리면, 번역본 검색은 원문 문서의 정확한 문자열(JIRA, HowToCommit)과의 어휘적 겹침을 잃어 오히려 점수가 떨어질 수 있다.
2. **두 후보 다 애매하게 낮은 점수가 나오는 경우**: 원본(혼합 언어)도 번역본(전체 번역)도 정답 문서와 딱 맞아떨어지지 않아, "더 높은 쪽 채택" 로직이 둘 다 나쁜 것 중 덜 나쁜 것을 고르는 상황이 될 수 있다.

다만 낙관적으로 볼 부분도 있다. 지금 구조가 **원본 질의어를 버리지 않고 번역본과 나란히 검색해서 비교**하기 때문에, 번역이 고유명사를 망쳐도 원본(고유명사가 살아있는 버전)이 이미 대안으로 존재한다. 즉 최악의 경우에도 "번역만 하고 원본을 버리는" 설계보다는 안전하다. 문제는 **번역 프롬프트가 지금 고유명사 보존을 명시적으로 지시하지 않는다**는 점이다 (`TRANSLATE_PROMPT`, `src/retriever.py`).

### 제안
- **즉시 반영 가능(저비용)**: `TRANSLATE_PROMPT`에 "페이지 제목, 제품/시스템명, 코드 식별자, 이슈 트래커 이름 같은 고유명사는 번역하거나 음차하지 말고 원문 그대로 남겨라"라는 지시를 추가한다. 번역 모델(Claude/Nova 계열)은 이런 지시를 잘 따르는 편이라 효과 대비 비용이 낮다.
- **검증 우선**: 코드를 더 손대기 전에, `evaluation/test_queries.csv`에 혼합 언어 질문을 2~3건 추가해 실제로 점수가 얼마나 떨어지는지 먼저 재보는 걸 권한다. 지금은 걱정이지 실측된 문제가 아니다 — 추측으로 구조를 더 복잡하게 만들기 전에 데이터로 확인하는 게 순서에 맞다.
- **문제가 실측되면 다음 단계**: 고유명사를 정규식(대문자로 시작하는 CamelCase, 영문 대문자 약어 등)으로 추출해 번역 전에 플레이스홀더로 치환하고 번역 후 복원하는 "보호-번역-복원" 방식을 검토한다. 다만 이건 오탐(일반 영단어를 고유명사로 오인)의 위험이 있어 실측 없이 먼저 넣지 않는 걸 권한다.

## 2. 이미지가 포함된 페이지의 임베딩 정확도

### 현재 상태
`crawl_confluence.py`는 `markdownify`로 HTML을 마크다운화하는데, 이미지 태그는 `![alt](src)` 형태로만 남고 이미지 내용 자체는 전혀 처리하지 않는다. 지금 크롤링한 HADOOP2 문서 7건은 대부분 설명형 텍스트/코드라 이 공백이 드러나지 않았지만, 실무 컨플루언스로 교체하면 아키텍처 다이어그램, 스크린샷, 캡처된 표 등이 흔하므로 이 공백은 실질적인 문제다.

### 검토: 제안하신 "그림/도표/문서 분류 + 히스토그램" 접근
- **그림(사진/일러스트) → 캡션 생성**, **도표 → Mermaid 변환**, **문서(스캔/캡처) → OCR**이라는 3분류 자체는 합리적이다. 각 유형마다 "텍스트로 바꿨을 때 가장 쓸모 있는 표현 방식"이 다르기 때문이다.
- **히스토그램(배경색 비중)으로 사진 vs 비-사진(도표/문서)을 가르는 것**은 컴퓨터 비전에서 실제로 쓰이는 값싼 휴리스틱이다(사진은 색 분포가 연속적이고 다양하고, 다이어그램/스크린샷은 배경이 단색이고 색 수가 적다). 이 1단계 분류는 그대로 써도 된다.
- **문제는 그다음 단계다: "도표"와 "문서"를 히스토그램만으로 가르기 어렵다**고 하신 게 맞다. 플로우차트(도표)도 스크린샷(문서)도 둘 다 "배경 많고 색 단순"한 이미지라 색 분포 통계로는 잘 구분되지 않는다. 이 둘의 실제 차이는 색이 아니라 **내용의 구조**(도표=도형+화살표+짧은 라벨, 문서=촘촘한 문단 텍스트)다. 색 히스토그램은 애초에 이 구분에 맞는 신호가 아니다.

### 제안
색 통계 대신 **텍스트 밀도**를 분류 신호로 쓰는 걸 권한다. 구체적으로:

1. 1단계(사진 vs 비사진)는 제안하신 대로 히스토그램으로 값싸게 거른다.
2. 비사진으로 분류된 이미지에는 **가벼운 OCR을 먼저 한 번 돌려서 그 결과 자체를 분류 신호로 쓴다.**
   - OCR이 이미지 면적의 상당 부분을 뒤덮는 촘촘한 텍스트를 높은 신뢰도로 뽑아내면 → **문서**로 분류, 그 OCR 결과를 그대로(또는 LLM으로 정리해서) 저장.
   - OCR 결과가 짧고 듬성듬성하거나 신뢰도가 낮으면(도형 안의 짧은 라벨 몇 개만 잡힘) → **도표**로 분류, 비전 LLM에게 Mermaid/설명 생성을 요청.
   - 즉 "OCR이냐 LLM이냐"를 미리 정하는 게 아니라, **OCR을 분류기 겸 1차 추출기로 먼저 쓰고, 그 결과로 다음 단계(그대로 쓸지 vs LLM에 다시 맡길지)를 결정**하는 순서다.
3. **더 간단한 대안(이번 프로젝트 규모에는 이쪽을 추천)**: 별도 히스토그램 분류기·OCR 엔진을 새로 붙이지 않고, 비전 지원 Bedrock 모델(우리가 이미 쓰는 Claude Sonnet 계열)에게 이미지 하나당 한 번, "사진이면 한 문단으로 설명하고, 도표/플로우차트면 Mermaid로, 문서/표 캡처면 보이는 텍스트를 그대로 옮겨 적어라"라는 프롬프트로 **분류+추출을 한 번에** 맡기는 방법이다. 이미지 수가 많지 않은 사내 온보딩 문서 규모(페이지 20~30개 수준)에서는 파이프라인을 새로 만드는 것보다 이쪽이 구현·유지보수 비용이 훨씬 낮다. 이미지 수가 수백~수천 장으로 커지면 그때 위 2단계(히스토그램+OCR로 값싸게 거르고, 필요한 것만 LLM에 보내는) 방식으로 비용을 낮추는 걸 고려하면 된다.

### 범위
크롤링한 7개 문서에는 원래 이 문제가 드러나지 않았고, MVP 범위(`documents/SERVICE.md` 9절 "초기 구현 범위")에도 이미지 처리는 없었다.

## 3. MCP로 "필요한 API만 상황에 맞게 전달"하면 실제로 부하/성능이 해결되는가

### 먼저 바로잡을 점
MCP 프로토콜 자체는 "상황에 맞는 API만 골라서 전달"하는 기능을 갖고 있지 않다. 우리 코드가 실제로 하는 일을 보면 명확하다 — `src/agent.py`의 `_get_mcp_tools()`는 `client.get_tools()`로 MCP 서버가 등록한 도구를 **전부** 가져오고, `build_agent()`는 그걸 조건 없이 전부 `create_agent(tools=[...])`에 넘긴다. "필요한 것만 그때그때 골라 전달"은 MCP가 대신 해주는 게 아니라, **누군가 설계해서 직접 구현해야 하는 별개의 문제**다. 이 점을 먼저 짚어야 다음 질문(직접 tools로 넣을 때는 어떻게 하는가)에 대한 답도 같은 선상에서 나온다.

### 실제로 성능/부하에 영향을 주는 것은 무엇인가
- **LLM 쪽 부하(정확도·비용)**: 에이전트에게 넘기는 도구가 많을수록 매 턴 프롬프트에 도구 스키마가 그만큼 더 들어가 토큰 비용이 늘고, 비슷한 도구가 많으면 모델이 잘못된 도구를 고르는 빈도도 올라간다(이른바 "tool 과잉" 문제). 이건 **도구가 MCP로 왔든 직접 `@tool`로 정의했든 동일하게 발생**한다. 지금 우리가 컨플루언스의 수십 개 REST 엔드포인트를 다 노출하지 않고 `get_page`/`search_confluence` 두 개로 추려둔 것 자체가 이 문제에 대한 실질적인 해법이고, 이건 MCP 여부와 무관한 **도구 설계(큐레이션)의 문제**다.
- **네트워크/서버 쪽 부하**: MCP를 쓰든 안 쓰든, 에이전트가 `search_confluence`를 호출하면 실제로 Confluence 서버에 HTTP 요청이 나간다. MCP가 이 요청 자체를 줄여주거나 컨플루언스 서버의 부하를 낮춰주지 않는다. MCP는 **에이전트 프로세스와 도구 실행 프로세스를 분리**해줄 뿐이다(우리 구조에서는 `tools.py`를 별도 stdio 서브프로세스로 띄움).
- **오히려 우리 구조에서 실측된 MCP의 비용**: `run_query()`는 호출될 때마다 `_get_mcp_tools()`로 **매번 새 MCP 서브프로세스를 띄운다.** 실제 로그에서 FastMCP 배너가 요청마다 출력되는 걸 볼 수 있었는데, 이건 순수 Python 함수 호출(예: `retriever.rag_search`)보다 프로세스 기동 오버헤드가 매 요청마다 추가된다는 뜻이다. 즉 지금 우리 프로젝트의 도구 2개 규모에서는, MCP가 부하를 줄여주기는커녕 지연 시간을 더 늘리는 쪽에 가깝다.

### "많은 API를 도구로 직접 노출할 때"는 어떻게 해결하는가
결론적으로 도구 수가 많을 때의 진짜 해법은 MCP냐 직접 정의냐가 아니라 다음 세 가지다.

1. **큐레이션**: 원본 API를 1:1로 다 도구화하지 않는다. 목적에 맞는 소수의 합성 도구(예: "검색", "페이지 조회", "하위 페이지 목록")로 추상화한다 — 지금 우리가 한 것과 동일한 원칙이다.
2. **여러 개의 전문 에이전트로 분리 + 라우팅**: 도구가 정말 많고 성격이 다양하면 하나의 에이전트에 다 몰아넣지 않고, 이 저장소 day6/day7의 `langgraph_supervisor` 패턴처럼 슈퍼바이저가 요청을 알맞은 하위 에이전트(그리고 그 에이전트의 작은 도구셋)로 라우팅한다. 이게 "상황에 맞는 도구만 쓰게 하는" 실질적인 방법이다.
3. **동적 도구 선택(tool retrieval)**: 도구 카탈로그가 너무 커서 정적 큐레이션도 어려우면, 질문을 임베딩해서 가장 관련 있는 도구 설명 k개만 그 턴의 컨텍스트에 넣는 "도구용 RAG"를 직접 구현하는 방법이 있다. 이것도 MCP가 자동으로 해주는 게 아니라 에이전트 쪽에서 추가로 만들어야 하는 로직이다.

MCP를 쓰는 진짜 이유는 부하 감소가 아니라 **표준화**(다른 클라이언트/에이전트에서도 같은 서버를 재사용 가능)와 **프로세스 격리**(도구 서버가 죽어도 에이전트 프로세스는 안 죽음)다. 지금 이 프로젝트에서 MCP를 채택한 이유도 SERVICE.md 상으로는 이 저장소의 day4~7 MCP 패턴을 그대로 재사용/증명하는 학습 목적이 크고, 도구가 2개뿐인 지금 규모에서 순수 성능만 보면 직접 `@tool`로 넣는 쪽이 오히려 더 가볍다는 점은 솔직히 밝혀둔다.

### 제안
- 지금 규모(도구 2개)에서는 성능 최적화보다 **정확성**이 우선이니 현재 구조를 유지한다.
- 도구가 늘어날 계획이 생기면, 새 REST 엔드포인트를 1:1로 도구화하지 말고 위 세 가지(큐레이션 → 멀티 에이전트 라우팅 → 동적 도구 선택) 순서로 검토한다.
- MCP 서브프로세스 기동 비용이 실제로 체감되면(1.5일 범위 밖이지만), `_get_mcp_tools()`를 요청마다 새로 만들지 않고 서버 프로세스 시작 시 한 번만 만들어 재사용하도록 캐싱하는 것도 고려한다.

## 4. `search_confluence`가 스페이스 범위를 안 지켜서 생긴 환각(처럼 보이는) 사례

### 문제 상황
새 평가셋(`test_queries.csv`, negative 카테고리)으로 실측하다가, "Kafka 클러스터에 새 Topic을 만드는 방법"이라는 범위밖 질문에 에이전트가 **모른다고 답하지 않고 `AdminClient` 코드까지 곁들인 상세한 답**을 내놨다. 처음엔 모델이 사전 지식(pretrained knowledge)으로 답한 환각이라고 의심했다.

### 실제 원인 (trace로 확인)
`src/tools.py`의 `search_confluence(cql)`이 에이전트가 보낸 CQL을 아무 제한 없이 그대로 실행하고 있었다. `rag_search`가 실패하자 에이전트는 `search_confluence`로 폴백했는데, 이 CQL 질의에 스페이스 제한이 없어서 **cwiki.apache.org 전체**(HADOOP2뿐 아니라 실제 KAFKA·FLINK 등 수백 개 ASF 프로젝트 스페이스)를 검색했고, 진짜 KAFKA 스페이스의 `KIP-108`, `KIP-117`, `KIP-464` 같은 실제 문서를 찾아 `get_page`로 원문까지 읽어온 뒤 그 내용으로 정확한 답을 만들었다. 즉 **환각이 아니라 스코프(대상 스페이스) 위반**이었다 — 내용 자체는 사실이지만 SERVICE.md가 정한 "HADOOP2로 범위 고정" 결정을 어긴 것.

### 왜 눈에 안 띄었나
같은 negative 카테고리의 다른 두 질문("Hadoop 3.4 신규 보안 기능", "Spark 실행 계획 최적화")은 스코프 제한이 없어도 통과했다 — 그 주제들은 cwiki.apache.org 어디에도 실제 문서가 없어서, 스코프를 안 걸어도 우연히 결과가 없었을 뿐이다. Kafka는 우연히 cwiki.apache.org 안에 실제 프로젝트 스페이스가 있어서 이 구멍이 드러났다. **RAG 스코프는 잘 지켜졌지만, 실시간 검색(MCP 폴백) 쪽에는 같은 보호장치가 없었다.**

### 조치
`search_confluence`에서 호출자가 보낸 CQL을 `space = "{CONFLUENCE_SPACE_KEY}" AND (...)`로 서버 쪽에서 강제로 감싸도록 고쳤다(`CONFLUENCE_SPACE_KEY`는 `.env`로 교체 가능, 기본값 `HADOOP2`). 에이전트가 스페이스 조건을 CQL에 넣는 걸 "잊지 않기를" 기대하는 프롬프트 지침이 아니라, 도구 코드 자체가 범위를 보장하도록 만들었다. 같은 맥락에서 시스템 프롬프트에도 "검색으로 찾지 못한 내용은 사전 지식으로도 채우지 마라"는 지침을 별도로 강화해뒀다 — 이번 사례의 근본 원인은 아니었지만, 진짜로 아무 근거도 못 찾는 다른 상황에 대한 방어선으로 유지한다.

### 교훈
LLM이 지침을 어겨서 생긴 문제처럼 보여도, 먼저 도구가 실제로 무엇을 검색/조회했는지 trace로 확인해야 한다. 이번 건은 "모델이 나쁘게 행동했다"가 아니라 "도구가 허용 범위를 스스로 제한하지 않았다"였다 — 안전장치는 프롬프트(설득)가 아니라 도구 코드(강제)에 두는 게 더 신뢰할 수 있다는 걸 다시 확인했다.
