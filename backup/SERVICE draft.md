# SERVICE.md — 컨플루언스 온보딩 Agent

## 1. 배경 및 목적

SI/SM 프로젝트에 새로 투입되는 신입 멤버는 방화벽/보안 설정, 사내 시스템 가입, 개발환경 구축 가이드 등 온보딩에 필요한 정보를 컨플루언스에서 찾기 어렵다. 특히 개발환경 구축 가이드 같은 개발 관련 문서는 분량이 길고 구조가 복잡해, 본인에게 필요한 부분이 어딘지 모른 채 **문서를 처음부터 끝까지 한 줄 한 줄 꼼꼼히 읽어야** 원하는 답을 얻을 수 있다.

**현재(As-Is)**: 두 갈래의 비효율이 있다.
- 막히면 사수/멘토에게 메신저로 질문한다. 응답 자체는 빠르지만(체감 5분 이내), 문제는 속도가 아니라 **매번 다른 사람의 업무를 끊어야 하고 셀프서비스가 안 된다는 점**이다.
- 셀프서비스로 직접 컨플루언스를 찾아보더라도, 개발환경 가이드처럼 긴 문서는 필요한 절차/설정값이 문서 어디에 있는지 알 수 없어 **전체를 정독해야만** 실제로 필요한 한두 줄을 얻을 수 있다. 즉 "문서를 못 찾는 문제"뿐 아니라 "찾은 문서를 다 읽어야 하는 문제"도 있다.
- 프로젝트 도중에 합류한 신입은 애초에 **어떤 문서부터, 어떤 순서로 봐야 하는지 자체를 모른다.** 컨플루언스에는 문서가 흩어져 있을 뿐 우선순위나 읽는 순서를 알려주는 안내가 없다.

**목적**: 컨플루언스 문서를 검색·인용해 답하는 AI 에이전트로, 신입이 문서를 처음부터 끝까지 읽지 않고도 필요한 부분만 바로 얻게 하여 아래 순서로 가치를 낸다.

1. 신입 온보딩 소요 시간 단축 (최우선) — 문서를 검색하고 정독하는 시간 자체를 줄인다
2. 문서 자체의 최신화/품질 개선 유도 — 에이전트가 답을 못 찾은 질문을 로그로 남겨 문서 관리자에게 피드백
3. 프로젝트 투입 초기 리스크(설정 누락, 오작/버그) 감소

**ROI (비용 절감 중심)**: 온보딩 시간 단축은 곧 투입 인력의 생산 가능 시간 증가이며, 사수의 인터럽트 감소도 동일한 인건비 절감 효과로 이어진다.

## 2. 사용자 및 적용 범위

- **대상**: SI/SM 프로젝트에 온보딩하는 신입 멤버 (한국어 사용자).
- **규모**: 연간/분기 기준 약 10~50명 (중규모) 투입을 가정.
- **운영 단위**: PoC 단계에서는 프로젝트마다 개별 인스턴스로 운영. 효과가 검증되면 회사 전체가 공유하는 단일 서비스로 확장.
- **적용 범위**: 삼성SDS 내부 전용 생산성 도구. 고객사 납품/상품화는 이번 범위 밖.

## 3. 검증 목표

1.5일 개발에서는 실제 온보딩 페인포인트를 있는 그대로 재현하기보다, **MCP + RAG + 에이전트 파이프라인 아키텍처 자체가 동작하는지 검증**하는 것을 우선한다. 테스트에 쓰는 ASF(Apache Software Foundation) 공개 컨플루언스는 실무 컨플루언스로 교체 가능한 구조임을 증명하기 위한 스탠드인 데이터다.

## 4. 데이터

- **대상 스페이스**: Apache Hadoop의 `HADOOP2` 공간 (`cwiki.apache.org/confluence/display/HADOOP2`).
- 인증 없이 REST API 접근 가능함을 확인함 (`/confluence/rest/api/content?spaceKey=HADOOP2` 정상 응답).
- `HowToSetupYourDevelopmentEnvironment`, `HowToContribute`, `HowToCommit`, `HowToCodeReview`, `HowToRelease` 등 온보딩 매뉴얼과 유사한 문서가 존재.
- 레거시/마이그레이션 공지가 있는 공간이라 내용이 잘 바뀌지 않아 평가 재현성 측면에서 유리.
- **실제 데이터**이며 더미 데이터가 아니다.
- `data/`에는 사람이 직접 고른 온보딩 관련 핵심 페이지 **20~30개 URL 리스트**를 수동 작성해두고, 스크립트로 그 리스트만 일괄 수집해 저장한다 (하이퍼링크를 따라가는 자동 크롤러는 사용하지 않음).

## 5. 아키텍처

```
사용자(HTML 채팅 UI) → FastAPI(POST /query) → agent.py(create_agent, ReAct)
                                                    ├─ retriever.py : RAG 검색 (chroma_db)
                                                    └─ tools.py     : Confluence MCP 서버
                                                                       (실시간 페이지 조회 / CQL 검색)
```

- **`retriever.py` (RAG)**: `data/`에 사전 크롤링해둔 20~30개 페이지를 chroma_db로 임베딩해 의미 검색. day2/day6/day7과 동일한 RAG 패턴.
- **`tools.py` (MCP)**: Confluence REST API를 감싸는 자체 MCP 서버(day4~7의 `mcp_server.py` 패턴)로 두 도구를 제공한다.
  1. 특정 페이지 ID/URL로 최신 원문 조회
  2. CQL 기반 실시간 검색 (사전 크롤링되지 않은 문서를 찾기 위한 폴백)
- `agent.py`는 `langchain.agents.create_agent`로 만든 단일 ReAct 에이전트로, `rag_search`, `confluence_live_search`, `confluence_get_page` 세 도구를 모두 갖되 시스템 프롬프트로 "먼저 로컬 검색, 부족하면 실시간 검색" 순서만 지침한다. 고정 LangGraph 분기 그래프는 쓰지 않는다.
- Confluence base URL/인증 토큰은 `.env`로 추상화해, 설정만 바꾸면 사내 컨플루언스로 교체 가능하게 한다.

## 6. 기능 요구사항

- **검색/답변**: 로컬 RAG 검색 → (유사도 임계값 미달 시) 실시간 CQL 검색 → (그래도 없으면) "모른다"고 답변하는 폴백 순서를 에이전트가 자율 판단해 수행한다.
- **응답 형식**: 문서 전체를 링크만 던지는 게 아니라, 질문과 관련된 부분만 **발췌·요약한 한국어 답변** + 출처 링크/원문 인용(영어 원문 그대로)을 함께 제공해 사용자가 긴 문서를 처음부터 끝까지 읽지 않아도 되게 한다. 관련 문서를 못 찾으면 명시적으로 "모른다"고 답해 환각을 방지한다.
- **언어**: 요약/설명은 한국어, 출처 인용구는 영어 원문 그대로 유지해 번역 오류로 인한 정보 왜곡을 막는다.
- **대화 방식**: 단일 턴. 이전 질문/맥락을 참조하는 멀티턴 메모리는 필요 없다.
- **API 계약**: `POST /query`, 입력은 `question` 필드. 응답은 `answer`, `contexts`, `trace` 세 키로 반환한다.
  - `trace`는 day7 `local_tracer.py`/`trace.jsonl` 패턴처럼 도구 호출 단계(어떤 검색어로 RAG를 호출했는지, 문서 ID/유사도, MCP 호출 여부와 결과)를 기록한다.
- **읽기 순서 가이드 (후순위)**: "뭐부터 봐야 하나요?" 류의 질문에는, 별도 고정 체크리스트가 아니라 **에이전트가 그때그때 RAG로 찾은 문서들을 종합해 추천 순서를 동적으로 생성**해 답한다. 정적 데이터를 따로 유지하지 않는 대신, 질문마다 순서가 달라지거나 근거 없이 순서를 지어낼 위험은 감수한다.

## 7. 비기능 요구사항

- 실시간 CQL 검색이 타임아웃/장애가 나면 RAG 결과만으로 조용히 계속 진행한다. `trace`에는 실패를 기록하되 사용자에게 별도 에러를 노출하지 않는다.
- 엄격한 응답 지연 목표는 두지 않는다 (데모 수준으로 충분).
- 에이전트/판정 모델 호출 시 **temperature=0**으로 고정해 재현성을 확보한다.

## 8. 초기 구현 범위 (MVP vs 후순위)

- **1차 (반드시 데모에서 동작)**: `retriever.py` RAG 검색 + 출처 인용 + 유사도 임계값 기반 "모름" 판단 + `trace` 기록. 이것만으로도 아키텍처 검증이라는 핵심 가치를 증명할 수 있다.
- **후순위 (시간이 부족하면 가장 먼저 포기)**:
  1. `tools.py`의 실시간 CQL 검색(MCP 라이브 폴백).
  2. 읽기 순서 가이드(에이전트가 문서를 종합해 추천 순서를 동적으로 생성하는 기능).
  - 둘 다 여유가 있을 때 추가하는 스트레치 목표다.

## 9. 하지 않을 것

- 멀티턴 대화(세션 내 맥락 유지) 구현하지 않는다.
- 엄격한 응답 지연 목표를 두지 않는다.
- 고객사 납품/상품화, 별도 사업계획서 작성은 이번 범위 밖이다.
- 하이퍼링크를 따라가는 자동 크롤러는 만들지 않는다 (수동 URL 리스트만 사용).
- 실시간 검색 실패를 사용자에게 에러로 노출하지 않는다.

## 10. 평가 계획

- **`test_queries.csv`** (`evaluation/`): 컬럼은 `question`(한국어), `category`(정상/범위밖), `expected_source_url`.
  - 정상 케이스: HADOOP2 문서로 답변 가능한 질문 7~8건, 정답 출처 페이지 URL 명시.
  - 범위밖 케이스: 관련 문서가 없어 "모른다"로 응답해야 하는 질문 2~3건.
- **평가 리포트**: 질문별 점수 + 판정 사유를 CSV/JSON으로 기록하고, 마지막에 전체 통계(평균 점수, 통과율)를 요약한다.
- **LLM-judge rubric**: 출처 정확성을 최우선으로 채점 (인용 URL이 `expected_source_url`과 일치/포함하는지).
- **성공 기준**:
  - 질문당 5점 만점 중 평균 4점 이상이면 해당 질문 통과.
  - `test_queries.csv` 10건 중 7건(70%) 이상 통과하면 오늘 산출물을 "성공"으로 본다.
